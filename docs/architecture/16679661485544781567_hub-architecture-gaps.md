# Hub Architecture Gaps: Registry → Plugin → Hub Transformations

## Problem Statement

Current goal: From any `ModelRegistry`, morph into a plugin; from any plugin, generate a hub.

```
ModelRegistry ──→ CllientActivation ──→ Plexus
     ↑                    ↑                  ↑
  (library)           (plugin)            (hub)
```

The user should be able to:
1. Import cllient as a library
2. Create a ModelRegistry
3. Convert it to a plugin with one call
4. Optionally spawn a hub around that plugin

Currently, this requires manual builder code in the substrate project.

## Using hub-macro

The `hub-macro` crate already provides `#[hub_methods]` to derive `Activation`:

```rust
#[hub_methods(namespace = "cllient", crate_path = "substrate")]
impl CllientActivation {
    #[hub_method]
    async fn complete(&self, request: CompletionRequest)
        -> impl Stream<Item = CompletionEvent> { ... }
}
```

**Key insight**: The macro's `crate_path` parameter controls where generated code looks for types (`Activation`, `PlexusStream`, `wrap_stream`, etc.).

## Current Architecture Summary

### What Exists

```rust
// In substrate/src/builder.rs - manual composition
let plexus = Plexus::new()
    .register(Echo::new())
    .register(Bash::new())
    .register_hub(Solar::new());
```

**Key traits:**
- `Activation` - Plugin interface (namespace, call, schema)
- `ChildRouter` - Nested routing for hubs
- `ActivationObject` - Type-erased plugin storage

**Key macro:**
- `#[hub_methods]` - Generates Activation impl from method signatures

### The Compile-Time Wall

Everything is statically bound:
1. Plugins are Rust types implementing Activation
2. Registration happens in builder.rs code
3. hub-macro generates code at compile time
4. No runtime plugin discovery

The `hypermemetic/hub-core` crate already has all the types we need:

```
hub-core/src/
├── plexus/
│   ├── plexus.rs      # Activation trait, Plexus, PlexusError
│   ├── streaming.rs   # PlexusStream, wrap_stream()

│   └── types.rs       # PlexusStreamItem, StreamMetadata
├── activations/
│   ├── echo/          # Example using hub-macro
```

**Key exports from hub-core:**
- `Activation` trait
- `PlexusStream` type
- `wrap_stream()` helper
- `PlexusError`, `PluginSchema`, etc.
- Already depends on `hub-macro`

**No circular dependency** - hub-core doesn't depend on cllient:
```
hub-core ←── cllient (can depend on hub-core)
    ↓
hub-macro
```

## Gap Analysis

### Gap 1: substrate Not Yet Using hub-core

**Problem**: substrate has duplicated plexus types instead of using hub-core.

**Solution**: Migrate substrate to depend on hub-core and re-export its types.

---

### Gap 2: No Library-Side Plugin Factory

**Problem**: A library can't expose "make me a plugin" functionality.

```rust
// Doesn't exist:
let plugin = cllient::as_plugin(registry);
plexus.register(plugin);
```

**Current state**: The consuming application must:
1. Know how to construct the Activation impl
2. Import internal types from cllient
3. Write registration code in their builder

**Why this matters**: cllient users shouldn't need to understand substrate internals.

---

### Gap 3: No Plugin-to-Hub Transformation

**Problem**: No way to take a single plugin and spin up a hub around it.

```rust
// Doesn't exist:
let hub = plugin.into_plexus();
hub.serve("0.0.0.0:8080").await;
```

**Why this matters**: For single-library use cases, users want standalone serving without plexus internals.

---

### Gap 4: No Embedded Hub Binary

**Problem**: Libraries can't ship a ready-to-run hub binary.

**Why this matters**: cllient should provide `cllient-hub serve --port 8080` without users wiring up substrate.

---

## Architectural Options

### Option A: Thin Trait Crate (substrate-core)

Extract minimal types to a small crate:

```
substrate-core/
├── Cargo.toml  (minimal deps: async-trait, serde, futures)
├── src/
│   ├── activation.rs    # Activation trait
│   ├── stream.rs        # PlexusStream, PlexusStreamItem
│   ├── schema.rs        # PluginSchema, MethodSchema
│   └── error.rs         # PlexusError
```

**Benefits:**
- Libraries depend on substrate-core (tiny)
- Substrate depends on substrate-core + adds Plexus, RPC, etc.
- No breaking changes to existing code

**Drawbacks:**
- Adds another crate to maintain
- Version coordination required

---

### Option B: Feature-Gated Plugin Support

Keep everything in substrate but gate heavily:

```toml
[features]
core = []  # Just traits
hub = ["jsonrpsee", "...]  # Full hub support
```

**Benefits:**
- Single crate
- Simpler versioning

**Drawbacks:**
- Feature flags are viral (cllient exposes them)
- Still a heavier dependency than needed

---

### Option C: Plugin Protocol (Schema-First)

Define plugins via schema, not Rust traits:

```yaml
# cllient-plugin.yaml
namespace: cllient
version: 1.0.0
methods:
  - name: complete
    input: CompletionRequest
    output: stream CompletionEvent
  - name: models
    output: stream ModelEvent
```

Runtime loads schema and dispatches via generic handler.

**Benefits:**
- Language-agnostic plugins
- Dynamic composition
- No compile-time coupling

**Drawbacks:**
- Loses type safety
- Complex runtime dispatch
- Major architectural change

---

### Option D: Self-Contained Library Plugins (Recommended)

Libraries ship everything needed:

```rust
// In cllient/src/lib.rs (feature-gated)

#[cfg(feature = "hub")]
pub mod hub {
    use crate::ModelRegistry;

    /// Plugin wrapper for substrate integration
    pub struct CllientPlugin {
        registry: Arc<ModelRegistry>,
    }

    impl CllientPlugin {
        pub fn new(registry: ModelRegistry) -> Self { ... }

        /// Mount into an existing Plexus
        pub fn into_activation(self) -> impl Activation { ... }

        /// Create standalone hub (single plugin)
        pub async fn serve(self, addr: &str) -> Result<()> {
            let plexus = Plexus::new().register(self);
            plexus.serve(addr).await
        }
    }
}

// Usage:
let registry = ModelRegistry::new()?;
let plugin = CllientPlugin::new(registry);
plugin.serve("0.0.0.0:8080").await?;
```

**Benefits:**
- Library controls the experience
- Users get simple API
- Substrate details hidden
- Feature-gated to avoid bloat

**Drawbacks:**
- Each library duplicates hub setup code
- Still depends on substrate for Plexus

## Recommended Architecture

### Layer 1: substrate-core (new crate)

Minimal crate (~500 lines) with:

```rust
// substrate-core/src/lib.rs
pub trait Activation: Send + Sync {
    fn namespace(&self) -> &str;
    fn version(&self) -> &str;
    fn description(&self) -> &str;
    fn methods(&self) -> Vec<&str>;

    async fn call(&self, method: &str, params: Value) -> Result<PlexusStream, PlexusError>;
    fn plugin_schema(&self) -> PluginSchema;
}

pub type PlexusStream = Pin<Box<dyn Stream<Item = PlexusStreamItem> + Send>>;

#[derive(Debug, Clone, Serialize, Deserialize)]
pub enum PlexusStreamItem {
    Data { value: Value, source: String, path: Vec<String> },
    Error { message: String, code: Option<i32> },
    Progress { current: u64, total: Option<u64>, message: Option<String> },
    Done { summary: Option<Value> },
}
```

### Layer 2: substrate (existing, depends on substrate-core)

Full hub runtime:
- Plexus (registry + routing)
- RPC server (jsonrpsee)
- Child routing
- Handle resolution

### Layer 3: hub-macro (existing, depends on substrate-core)

Generates Activation impls. Works with substrate-core types.

### Layer 4: Library plugins (e.g., cllient)

```toml
# cllient/Cargo.toml
[dependencies]
substrate-core = "0.1"

[features]
hub = ["substrate"]

[dependencies.substrate]
version = "0.2"
optional = true
```

```rust
// cllient/src/plugin.rs
use substrate_core::{Activation, PlexusStream, PlexusStreamItem};

pub struct CllientActivation {
    registry: Arc<ModelRegistry>,
}

impl Activation for CllientActivation {
    fn namespace(&self) -> &str { "cllient" }
    // ... implement trait
}

impl CllientActivation {
    /// Create from registry
    pub fn from_registry(registry: ModelRegistry) -> Self {
        Self { registry: Arc::new(registry) }
    }
}

// With "hub" feature:
#[cfg(feature = "hub")]
impl CllientActivation {
    /// Serve as standalone hub
    pub async fn serve(self, addr: &str) -> Result<()> {
        use substrate::Plexus;
        let plexus = Plexus::new().register(self);
        plexus.serve(addr).await
    }

    /// Wrap into Plexus for composition
    pub fn into_plexus(self) -> substrate::Plexus {
        Plexus::new().register(self)
    }
}
```

### Usage Patterns

**Pattern 1: Embedded in larger hub**
```rust
use substrate::Plexus;
use cllient::CllientActivation;

let cllient = CllientActivation::from_registry(ModelRegistry::new()?);
let plexus = Plexus::new()
    .register(cllient)
    .register(other_plugin);
```

**Pattern 2: Standalone hub**
```rust
use cllient::CllientActivation;

let plugin = CllientActivation::from_registry(ModelRegistry::new()?);
plugin.serve("0.0.0.0:8080").await?;
```

**Pattern 3: Binary**
```rust
// cllient/src/bin/cllient-hub.rs
#[tokio::main]
async fn main() {
    let registry = ModelRegistry::new().unwrap();
    CllientActivation::from_registry(registry)
        .serve("0.0.0.0:8080")
        .await
        .unwrap();
}
```

## What Substrate Needs to Change

### 1. Extract substrate-core

Move these to substrate-core:
- `Activation` trait
- `PlexusStream` type
- `PlexusStreamItem` enum
- `PlexusError` type
- `PluginSchema` structs
- `wrap_stream()` helper

### 2. Make Plexus Accept External Activations

```rust
impl Plexus {
    // Existing
    pub fn register(self, activation: impl Activation + 'static) -> Self;

    // New: accept already-boxed
    pub fn register_dyn(self, activation: Arc<dyn Activation>) -> Self;
}
```

### 3. Add Standalone Serve Helper

```rust
// In substrate
pub async fn serve_plugin(plugin: impl Activation + 'static, addr: &str) -> Result<()> {
    Plexus::new().register(plugin).serve(addr).await
}
```

### 4. Hub-Macro Works with substrate-core

```rust
// hub-macro generates:
use substrate_core::{Activation, PlexusStream};  // Not full substrate
```

## Migration Path

### Phase 1: Create substrate-core
1. New crate with minimal types
2. Re-export from substrate for backwards compat
3. Update hub-macro to use substrate-core

### Phase 2: Update cllient
1. Depend on substrate-core (not substrate)
2. Implement Activation for CllientActivation
3. Feature-gate full hub support

### Phase 3: Add Convenience APIs
1. `CllientActivation::serve()` method
2. `cllient-hub` binary
3. Documentation for both patterns

### Phase 4: Update Other Plugins
1. Migrate existing activations to substrate-core
2. Update builder.rs for new patterns
3. Test all activation methods

---

## Success Criteria

1. **Minimal dependency**: `substrate-core` has no RPC/server deps
2. **Library-first**: cllient users can create plugins without understanding substrate
3. **Composable**: Plugins can be mounted into any Plexus
4. **Standalone**: Single plugin can serve as its own hub
5. **Binary-ready**: Libraries can ship hub binaries with one main() call
6. **Backwards compatible**: Existing substrate code continues to work
